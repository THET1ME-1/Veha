# Veha — проектный документ

> Дата: 27 июля 2026. Статус: утверждается.
> Сводит техническое задание, требования к доступу для ИИ-агентов и разбор
> визуальных референсов.

---

## 1. Что это

Календарь для Android с двумя свойствами, которых нет вместе ни у кого:

1. Он живёт на устройстве и работает без аккаунта, как Etar или Fossify Calendar.
2. Отдельные календари можно расшарить с людьми и подключить к ним ИИ-ассистента,
   не отдавая всю жизнь в Google.

Имя — **Veha** (веха, отметка на пути). Лицензия GPL-3.0. Распространение через
GitHub Releases, Obtainium и F-Droid. iOS не поддерживается.

### Четыре принципа, которые не обсуждаются

**Local-first.** Приложение полностью функционально без интернета и без аккаунта.
Синхронизация — слой поверх локальной базы, а не её основа.

**Наверх уходит только явно расшаренное.** Личные календари не покидают
устройство. В настройках всегда виден список того, что ушло на сервер.

**Сервер тупой.** Он хранит и раздаёт. Источник истины — устройство.

**Скорость важнее фич.** Календарь открывают на пять секунд по десять раз в день.
Холодный старт до отрисовки месяца — под 500 мс.

## 2. Границы и декомпозиция

Работа разбита на три независимых куска. Каждый доводится до конца до начала
следующего, и у каждого свой репозиторий.

| Этап | Репозиторий | Содержание | Когда |
|---|---|---|---|
| 1 | `THET1ME-1/Veha` | База, движок повторений, четыре вида, события, свои поля, напоминания, темы, .ics, локализация | Сейчас |
| 2 | `THET1ME-1/Veha` | Виджеты, задачи, быстрый ввод, подписка на .ics, статистика, блокировка | После релиза 1.0 |
| 3 | `THET1ME-1/veha-server` | Аккаунты, синхронизация, шаринг, MCP-эндпоинт, токены доступа, журнал | После того как модель данных устоялась на реальных пользователях |

Третий этап не начинается, пока формат событий не устоялся. Менять модель после
запуска синка дорого.

### Чего не делать никогда

iOS. Свой протокол синхронизации сверх описанного. Syncthing (он синхронизирует
файлы, а не базу, и при одновременной правке плодит конфликтные копии).
Разворачивание повторений на сервере. Realtime-подписки. Рекламу. Боковую панель.
Эмодзи вместо иконок. Supabase self-hosted (десяток контейнеров и 2 ГБ RAM против
цели «заводится на Raspberry Pi»).

## 3. Стек

**Клиент.** Flutter, Dart. База — SQLite через `drift`. Состояние — `riverpod`.
Повторения — `rrule` и `timezone`. Динамическая тема — `dynamic_color`. Цвет —
`material_color_utilities`. Иконки — `material_symbols_icons`. Уведомления —
`flutter_local_notifications`. Фоновый синк — `workmanager`. Сеть —
`connectivity_plus`.

**Сервер (этап 3).** Hono на TypeScript, Drizzle ORM. Два таргета из одного кода:
Cloudflare Workers с D1 для публичного инстанса и Node/Bun с файлом SQLite в
Docker для самохостинга. `docker-compose.yml` с томом `./data:/app/data`
обязателен — этого ждёт FOSS-аудитория.

**Дизайн-система.** Токены, шрифты и базовые виджеты берутся из
`THET1ME-1/m3-dna` git-зависимостью, а не копией. Единственное, что меняется под
Veha, — `defaultSeed`.

Фирменный seed: `0xFF41CCB5`, мята. Он задаёт вид приложения до того, как
пользователь выбрал свой цвет или включил Material You.

Соседние приложения занимают: бирюза `0xFF00B5C7` (Kadr, ScoreMaster),
папоротник `0xFF2E7D5B` (Fern), мёд `0xFFC0863E` (Wickly), роза `0xFFFF7E9B`
(Togetherly).

**Знать про этот оттенок.** На 182° режим «Сочно» (`vibrant`, дефолт ДНК)
выкручивает `primaryContainer` светлой темы до `#00FEDF` — это кислотная мята, а
роль отвечает за пилюли, индикатор навбара и FAB. Режим «Точь-в-точь»
(`fidelity`) даёт ровно `#41CCB5`. Снижение насыщенности seed не помогает:
`SchemeVibrant` берёт из seed только оттенок, хрому подставляет свою.

## 4. Модель данных

UUID генерирует клиент — без этого событие не создать офлайн. Удаление всегда
мягкое через `deleted_at`, физическая чистка раз в 90 дней, иначе сервер вернёт
удалённое обратно при следующем синке. `updated_at` обновляется при любой правке,
конфликт разрешается по нему: побеждает более позднее.

### Calendar

```
id            TEXT PRIMARY KEY   UUID с клиента
name          TEXT
color         INTEGER            ARGB, любой цвет из пикера
icon          TEXT               имя иконки Material Symbols
is_visible    BOOLEAN
is_shared     BOOLEAN            ушёл ли на сервер
owner_id      TEXT NULL
sort_order    INTEGER
created_at    INTEGER
updated_at    INTEGER
deleted_at    INTEGER NULL
```

### Event

```
id              TEXT PRIMARY KEY
calendar_id     TEXT
title           TEXT
description     TEXT NULL
location        TEXT NULL
start           INTEGER            UTC epoch ms
end             INTEGER
timezone        TEXT               IANA, напр. Europe/Chisinau
is_all_day      BOOLEAN
color           INTEGER NULL       NULL = цвет календаря
icon            TEXT NULL
event_type_id   TEXT NULL
rrule           TEXT NULL          RFC 5545
recurrence_id   TEXT NULL          ссылка на родительский ряд
original_start  INTEGER NULL       какой экземпляр переопределён
status          TEXT               confirmed / tentative / cancelled
availability    TEXT               busy / free
created_at      INTEGER
updated_at      INTEGER
deleted_at      INTEGER NULL
```

**Событие не задача.** Отметки выполнения у события нет и не будет: запланированное
мероприятие либо состоялось, либо нет, и галочка здесь ничего не сообщает. Чекбокс
с референса не переносим. Задачи — отдельная сущность второго релиза, вот у них
отметка выполнения есть по смыслу.

### Остальные таблицы

```

Reminder             id, event_id, minutes_before, method
EventType            id, name, icon, color, default_duration, default_reminders
SyncQueue            id, entity_type, entity_id, operation, payload, created_at, retry_count
```

### Индексы

`(calendar_id, start)`, `(start, end)`, `(deleted_at)`.

## 5. Повторяющиеся события

Самая трудная часть, закладывается сразу.

Периодичность: ежедневно, еженедельно, ежемесячно, ежегодно. Каждые N единиц. По
дням недели. По числу месяца и по позиции («второй вторник»). Окончание: никогда,
после N повторов, до даты.

Правки: один экземпляр, «этот и все последующие», пропуск одного, удаление ряда.

Ряд разворачивается только для видимого диапазона плюс месяц с каждой стороны,
результат кешируется в памяти. Все экземпляры в базе не материализуются никогда.

Отдельные тесты на перевод часов и смену часового пояса — эта часть ломается
тихо, и без тестов ошибку находит пользователь, а не разработчик.

## 6. Цвет и иконки

### Почему у всех пять цветов, а у нас любой

Стандартные календари ограничивают палитру по трём причинам. В формате `.ics`
свойство `COLOR` принимает только именованные CSS-цвета, а Google Calendar API
хранит цвет как `colorId` из фиксированного списка — произвольный hex при
синхронизации теряется. Тёмно-синий фон с чёрным текстом читать невозможно, а
курируемая палитра гарантирует контраст. Произвольный hex конфликтует с тональной
палитрой Material You и выглядит инородно.

Решение Veha: пользователь выбирает любой цвет в полноценном пикере (HSV-поле,
hex-поле, пипетка), но выбранный цвет не идёт в отрисовку напрямую. Он подаётся
seed'ом в `material_color_utilities`, оттуда генерируется тональная палитра в
пространстве HCT, и событие рисуется тонами под текущую тему:

- светлая тема: фон события — тон 90, текст и иконка — тон 10;
- тёмная тема: фон — тон 30, текст и иконка — тон 90.

Любой цвет читаем, согласован с темой и при этом действительно любой. Этого не
умеет ни один существующий календарь, и это идёт в описание приложения.

При экспорте в `.ics` цвет округляется до ближайшего именованного, оригинальный
hex сохраняется в `X-`-свойстве.

Палитра пресетов остаётся быстрым выбором, пикер прячется за кнопкой «свой цвет».
Последние использованные цвета сохраняются. Цвет календаря наследуется событиями,
у события переопределяется.

### Иконки

Перед названием события и календаря — иконка Material Symbols, не эмодзи. Эмодзи
различаются между устройствами и ломают тональность.

Пакет `material_symbols_icons` под Apache 2.0, около 3500 иконок. Пикер — сетка с
поиском и группировкой по категориям. Стиль Rounded. Иконка красится в тон цвета
события. Иконка есть у события, календаря и типа события.

**Грабли с размером APK.** Иконка выбирается по строковому имени, и tree-shaking
такие обращения не видит: он либо выбросит нужное, либо придётся отключать
shaking и тащить весь шрифт. Решение — явный белый список допустимых иконок в
коде, сгенерированный скриптом, с контролем итогового размера сборки.

## 7. Виды календаря: разбор референсов

Референсы дают три экрана: таймлайн-цепочку дня, неделю колонками пилюль и месяц
в выдвижном листе. Взять их как есть нельзя — это iOS-приложение с плоской
палитрой из шести фиксированных красок. Ниже разобрано, что берём, что меняем и
почему.

| С референса | Что делаем в Veha |
|---|---|
| Пилюли полного радиуса, цепочка на нити | Берём целиком. Это визитная карточка. |
| Плоские яркие краски (коралл, синий, зелёный) | Заменяем тонами HCT из палитры события. Форма остаётся, цвет становится частью системы. |
| Круглая иконка внутри пилюли | Берём, добавляем морфинг фигуры при отметке выполнения. |
| Круглый чекбокс справа | Не берём. Событие не задача, отмечать его выполненным нечего. Освободившееся место справа уходит под свои поля. |
| Полоса «Luteal / Period» над таймлайном | Обобщаем до полосы многодневного события, см. §7.5. Трекинг цикла не встраиваем — пользователь собирает его сам через свой тип события. |
| Кольца «Energy Level» | Не берём. Чужая фича из другого продукта. |
| Нижний таббар iOS с разделом AI | Заменяем на `NavigationBar` M3. Разделы — Календарь, Список, Доступ, Настройки. |
| Заголовок «April **2020**» с контрастом начертаний | Берём и усиливаем: месяц Unbounded Bold, год Onest Light акцентным цветом. Фирменная деталь экрана. |
| Выдвижной лист с месяцем | Берём. Перетаскиваемый по высоте bottom sheet — ключевой паттерн взаимодействия. |

### 7.1 День: два вида, оба обязательны

День показывается двумя способами, переключение — тем же сегментированным
контролом, что и месяц с неделей. Ни один не заменяет другой: цепочка отвечает на
вопрос «что у меня сегодня», часы — «когда я свободен».

**Цепочка.** Вертикальная лента: слева колонка времени, справа события. Событие —
пилюля полного радиуса, иконка стоит **по центру пилюли**, а не прижата к верху.
Пилюли соединены тонкой линией `outlineVariant` — получается непрерывная цепочка
дня. Пустые часы не занимают место.

**Часы.** Настоящая шкала времени: высота пропорциональна длительности, пустые
промежутки видны, пересекающиеся события делят ширину. Иконка так же по центру
своего блока.

Под названием — поля, выбранные пользователем (см. §7.7): длительность, место,
кабинет, преподаватель, признак повтора, признак синхронизации. Набор задаётся на
уровне типа события, а не зашит в код.

Под текущим временем — линия «сейчас».

### 7.2 Неделя колонками пилюль

Семь колонок, события — вертикальные пилюли, высота пропорциональна
длительности, иконка **по центру пилюли**. Выходные и прошедшие дни приглушены.

Самый узнаваемый вид. Требует аккуратной работы с наложением: пересекающиеся
события делят ширину колонки.

### 7.3 Месяц

Классическая сетка, тап по дню раскрывает лист с этим днём.

Россыпь мелких кружков под числом отвергнута: на плотном месяце это визуальный
мусор, по которому ничего не прочитать. Вместо неё день показывает **полосу
занятости** — одну горизонтальную ленту под числом, поделённую на сегменты по
цветам календарей, где длина сегмента пропорциональна времени. Пустой день
остаётся пустым, забитый читается как сплошная лента.

Альтернативы, между которыми выбираем по макету: чипы с названиями (две-три
пилюли с текстом плюс «+N») и тонированная ячейка (фон дня красится тоном 95
преобладающего календаря).

### 7.4 Дни лентами

Пятый вид, самый плотный по смыслу на единицу экрана. Вертикальный список дней,
каждый день — плашка:

- слева крупная дата: число `displayMedium` в Unbounded 800, месяц строкой ниже
  светлым начертанием — тот же приём контраста, что в шапке;
- справа горизонтальная шкала часов с чипами событий, подписи часов сверху;
- под свободным часом — кружок с плюсом: тап создаёт событие сразу в этот час.
  Это единственное место в приложении, где новое событие заводится без диалога
  выбора времени.

Плашка красится тоном 95 в светлой теме и 30 в тёмной по **преобладающему
календарю дня**, чипы внутри — своими цветами тона 40. Цвет тут работает, а не
украшает: пролистывая неделю, видно, чем занят каждый день, ещё не читая
названий.

Прошедшие дни приглушаются, сегодня получает обводку `primary`.

### 7.5 Общее

Свайп влево-вправо — соседний период. Переключение вида — сегментированный
контрол на четыре положения: День, Дни, Неделя, Месяц. Внутри «Дня» два
прочтения (часы и цепочка) переключаются парой иконок в шапке и свайпом вверх —
поэтому в контроле они занимают одно место, а не два.

Горизонтальная лента дат недели закреплена сверху. Bottom sheet с деталями дня
перетаскивается по высоте.

### 7.6 События длиннее дня

Абонемент на 30 дней, отпуск, курс, командировка — событие, у которого важна не
позиция внутри суток, а сам факт «идёт сейчас». Такие события не рисуются в сетке
часов, у них своё место:

- **в дне** — полоса над таймлайном с прогрессом: «Абонемент · 12-й день из 30»;
- **в неделе** — горизонтальная лента над колонками, тянется через захваченные дни,
  на краях недели обрезается стрелкой;
- **в месяце** — непрерывная лента через ячейки, скруглённая на первом и последнем
  дне.

Событие считается многодневным, когда `end - start` больше суток либо стоит флаг
`is_all_day` и дат больше одной. Отдельного типа в схеме для этого не нужно.

### 7.7 Свои поля события

Ни один календарь не даёт положить в событие кабинет, преподавателя или номер
абонемента. Veha даёт: пользователь заводит свои поля и сам решает, какие из них
видны в карточке.

**Модель.**

```
FieldDefinition
  id            TEXT PRIMARY KEY
  name          TEXT        «Кабинет», «Преподаватель»
  type          TEXT        text / number / date / time / duration /
                            select / checkbox / url / phone / person / money
  options       TEXT NULL   JSON со списком значений для select
  icon          TEXT NULL   иконка Material Symbols
  scope_type    TEXT        event_type / calendar / global
  scope_id      TEXT NULL   к какому типу или календарю привязано
  show_in_card  BOOLEAN     показывать в свёрнутой карточке
  sort_order    INTEGER
  created_at, updated_at, deleted_at

FieldValue
  event_id      TEXT
  field_id      TEXT
  value         TEXT        сериализованное значение
  PRIMARY KEY (event_id, field_id)
```

**Правила.**

Поля живут на типе события: завёл тип «Занятие» — у всех занятий появились
кабинет и преподаватель. Глобальные поля видны везде, поля календаря — у его
событий.

Карточка показывает максимум три поля, отмеченных `show_in_card`, в порядке
`sort_order`. Остальные видны на экране события. Ограничение не настраивается:
карточка на четыре строки перестаёт читаться, а таймлайн ради этого теряет
плотность.

Встроенные поля (место, участники, повтор, напоминание, календарь) участвуют в
том же списке видимости, что и свои. Человек не должен различать, что зашито в
приложение, а что он завёл сам.

При экспорте в `.ics` свои поля уходят в `X-`-свойства с префиксом `X-VEHA-`.
Импорт их читает обратно и создаёт недостающие определения.

Поиск ищет по значениям полей наравне с названием и описанием.

## 8. Навигация

Боковой панели нет. Никакого `Drawer`.

Нижняя `NavigationBar` на четыре раздела:

1. **Календарь** — три вида, переключаются сегментированным контролом и свайпом.
2. **Список** — ближайшие события, поиск, фильтр по типу и календарю.
3. **Доступ** — расшаренные календари, участники и токены для ИИ. До третьего
   этапа раздел скрыт.
4. **Настройки** — темы, цвет, язык, напоминания по умолчанию, бэкап, .ics.

Список календарей живёт в bottom sheet с главного экрана, не в разделе.

## 9. Доступ для ИИ-агентов

Раздел целиком относится к третьему этапу и требует серверного слоя.

### 9.1 Честное ограничение

ИИ живёт на чужих серверах. Чтобы что-то поменять, он должен куда-то постучаться,
а в телефон постучаться нельзя: он в кармане, за роутером, часто без сети.
Стучаться надо в сервер, куда телефон и так шлёт данные.

Отсюда следствие: фича работает только у тех, кто включил синхронизацию. У кого
календарь чисто локальный, её не будет. Это пишется прямо в интерфейсе, а не
выясняется опытным путём.

### 9.2 Форма — MCP плюс REST

Hono на Workers отдаёт MCP-эндпоинт, любой клиент подключается по ссылке с
токеном. Инструменты минимальные:

| Инструмент | Что делает |
|---|---|
| `list_calendars` | Календари, доступные этому токену, с правами по каждому |
| `list_events` | События за период по выбранным календарям |
| `create_event` | Создать событие |
| `update_event` | Изменить событие |
| `delete_event` | Удалить событие, только с подтверждением |
| `find_free_time` | Найти свободные окна нужной длины в диапазоне |

Обычный REST под `/api/v1` остаётся с тем же набором операций: не всё умеет MCP.

### 9.3 Токены

```
AccessToken
  id, user_id
  name              TEXT      имя агента, задаёт человек
  token_hash        TEXT      хранится только хеш
  prefix            TEXT      первые символы для показа в списке
  created_at, expires_at, last_used_at, revoked_at

AccessTokenScope
  token_id, calendar_id, can_write BOOLEAN

AccessLog
  id, token_id, at, tool, calendar_id, event_id,
  action    read / create / update / delete
  result    ok / denied / error
```

Токен выглядит как `cal_a8f3k2…` и передаётся заголовком `Authorization: Bearer`,
не в URL: URL оседает в логах прокси и в истории.

Правила, которые задают позиционирование:

- отдельный токен на каждого агента, со своим именем;
- галочками задаётся, какие календари видны и каждый — чтение или запись;
- срок жизни и отзыв в один тап;
- журнал: что и когда токен трогал.

Журнал — то, что превращает опасную фичу в аргумент. В Google Calendar не видно,
что именно делало стороннее приложение. Здесь видно.

### 9.4 Защита

**По умолчанию — только чтение и только личные календари.** Общие подключаются
отдельной галочкой с явным предупреждением.

**Инъекция через чужой текст.** Как только появятся общие календари, в описании
события может лежать текст, написанный другим человеком. Агент читает его как
часть своего контекста, и это классический вектор атаки. Поэтому поля, пришедшие
из общего календаря, отдаются агенту с флагом `untrusted: true` и обёрнуты
маркером «данные, не инструкции».

**Удаление требует подтверждения.** `delete_event` первым вызовом возвращает
описание того, что будет удалено, и требует повторного вызова с `confirm: true`.
Удаление мягкое, корзина живёт 30 дней.

**Ограничение частоты** на токен, чтобы сорвавшийся агент не выел базу.

### 9.5 Экран «Доступ»

Кнопка «создать ключ» → галочки по календарям и правам → приложение показывает
строку один раз → человек копирует её в ИИ. Дальше строка не показывается
никогда, хранится только хеш.

Карточка токена: имя, когда создан, когда истекает, когда последний раз
использовался, список календарей с правами, кнопка отзыва и журнал действий.

## 10. Синхронизация

Клиент пишет только в локальную базу и складывает изменение в `SyncQueue`.
Очередь схлопывается: пять правок одного события превращаются в одну запись.

Отправка при старте приложения, при появлении сети, по расписанию через
WorkManager и по кнопке вручную. Сервер отдаёт изменения с момента последнего
синка курсором по `updated_at`.

Конфликт: побеждает более позднее `updated_at`. Для общих календарей — слияние по
полям: один поменял время, другой название, применяются оба.

В интерфейсе видно состояние: «не синхронизировано, 12 изменений ждут».

Сквозное шифрование на старте не делаем. Оно ломает серверные уведомления и
поиск, а при выходе участника требует перевыпуска ключей. Возможность
закладывается, реализация позже.

## 11. Анимация

Material 3 Expressive построен на пружинной физике, а не на кривых Безье. Значит
`SpringDescription` и токены движения M3, а не `Curves.easeInOut` по умолчанию.

**Главная анимация — морфинг фигур.** Круглый контейнер иконки перетекает через
набор фигур: круг, лепесток, четырёхлистник, скруглённый квадрат. Применяется в
трёх местах и больше нигде:

- иконка события при отметке выполнения;
- FAB при открытии формы создания;
- индикатор загрузки вместо спиннера.

Этот элемент держит узнаваемость, и размазывать его по всему интерфейсу нельзя.

Остальное: переход между видами — общая ось; открытие события — container
transform от карточки к экрану; смена месяца — пружинный сдвиг с лёгким
перекрытием; отметка выполнения — пружина с небольшим перелётом; появление списка
— каскад с задержкой 20–30 мс, не больше.

Системная настройка «уменьшить движение» уважается: все переходы становятся
простым проявлением.

## 12. Производительность

Холодный старт до отрисовки текущего месяца — под 500 мс. Скролл месяцев и недель
— стабильные 120 fps на устройствах с высокой частотой.

Повторения разворачиваются только для видимого диапазона плюс месяц с каждой
стороны, результат кешируется. Развёрнутые экземпляры дальше видимого окна в
состоянии не держатся.

Запросы к базе идут через реактивные стримы drift, без пересборки всего дерева на
каждое изменение. Разбор `.ics` и импорт — в изоляте.

## 13. Локализация

Семь языков: русский, английский, украинский, румынский, польский, немецкий,
испанский.

`flutter_localizations` и ARB-файлы. Форматы дат и первый день недели берутся из
локали с возможностью переопределить вручную. Вёрстку проверять на немецком — там
самые длинные слова, именно он ломает макеты. Строки не склеиваются из кусков:
плейсхолдеры и plural-формы (в русском их три).

## 14. Порядок работ

1. Схема базы и модель данных — сразу с полями под повторения, свои поля и синк.
2. Движок повторяющихся событий с тестами на переводы часов и смену пояса.
3. Виды «месяц» и «день» в обоих прочтениях, создание и редактирование события.
4. Дизайн-система: динамические темы, генерация палитры из произвольного seed,
   пикер цвета, пикер иконок.
5. Напоминания.
6. Вид «неделя» колонками пилюль, морфинг фигур.
7. События длиннее дня: полоса в трёх видах.
8. Свои поля события: типы данных, редактор, видимость в карточке.
9. Экспорт и импорт `.ics` вместе с `X-VEHA-`-полями, бэкап базы.
10. Пользовательские типы событий, поиск по полям, локализация.
11. Релиз 1.0 на GitHub и F-Droid.
12. Второй релиз: виджеты, задачи, быстрый ввод, статистика.
13. Сервер: аккаунты, синхронизация, шаринг.
14. MCP-эндпоинт, токены, журнал доступа.

## 15. Что проверяем тестами

Движок повторений — перевод часов вперёд и назад, событие в 02:30 в ночь
перевода, смена часового пояса устройства, «второй вторник» на границе месяца,
правка «этого и последующих» в середине ряда.

Синхронизацию — схлопывание очереди, конфликт по `updated_at`, слияние по полям,
возврат мягко удалённого события.

Токены — истёкший, отозванный, попытка записи токеном на чтение, попытка
обратиться к календарю вне списка, удаление без подтверждения.

Свои поля — значение каждого типа туда и обратно через `.ics`, удаление
определения при живых значениях, событие с полем удалённого типа, поиск по
значению поля.

Многодневные события — событие через границу месяца, через границу года, событие
на весь день в часовом поясе с переводом часов.

Разбор `.ics` — файлы из Google Calendar, Apple Calendar и Etar.
